# 修正依頼から確認版まで

著者からの修正依頼を、漏れなく・余計な変化を起こさずに反映し、著者が確かめやすい形で返す。
一番の失敗は「頼まれていない所が動く」と「頼まれた所の取りこぼし」。どちらも、反映の前に依頼を一覧にし、反映の後に新旧のPDFを見比べる事で防ぐ。

このスキルのフォルダ（読み込み時に表示される Base directory）を `SKILL_DIR` と呼ぶ。共通の道具は `SKILL_DIR/../../scripts/`（本に `tools/kumihan-kit/` としてコピーしてあれば、そちらを使う）。

**まず本の `CLAUDE.md` を読む。** 本ごとの決まり（確認版に入れる物、コミットしてよいか、報告の書き方、ビルドの手順）は、このスキルより優先する。

## 1. 依頼を受け取って保存する

- 届いた物を `original-text/<今日の日付>/` に、そのままの形で保存する（文面は `.txt` に）。後で「何を頼まれ、どう直したか」を確かめる拠り所になる。
- ZIPは `python3 SKILL_DIR/../../scripts/unzip_ja.py <ZIP> <展開先>` で展開する。Windowsで作られたZIPは、普通に展開すると日本語のファイル名が化ける。
- 前回の確認版（`releases/` の一番新しい日付のPDF）を確かめておく。見比べの「旧」になる。

## 2. 依頼を一覧にする（直す前に）

依頼を1件ずつに分け、番号を付けて、それぞれ原稿のどこかを特定する。

| 番号 | 依頼の文面（原文のまま） | 原稿の場所 | 直し方 |
| --- | --- | --- | --- |

- **ページ番号はノンブル（ページに印刷された番号）で考える。** 依頼の「P.42」は、PDFの42枚目ではない（表紙・目次の分ずれる）。PDFの該当ページの文字を抜き出し、原稿を文字列で検索して場所を特定する。
- 「後ろから3行目」のような指定は、そのページを画像にして数える。
- 同じ語句が原稿に何箇所もある時は、依頼が1箇所なのか全部なのかを見極める。分からなければ、候補の箇所を示して聞く。
- 依頼が曖昧・矛盾している・組版上できない（「この行だけ字を大きく」で行が溢れる等）時は、直す前に、選択肢と推奨を添えて使う人に聞く。分かる所から先に進めてよい。
- 図版の差し替えは、新旧の画像の大きさ・解像度（表示する大きさで300dpi程度あるか）・色（白黒の本ならグレースケールに）・内容の違いを確かめて報告する。

## 3. 直す

- 原稿（`draft/*.md`）とCSSを直す。依頼の文言は勝手に整えない（表記の揺れに気づいたら、直さずに報告して聞く）。
- ルビ・圏点などの記法は、本の `CLAUDE.md` の「原稿の記法」に従う。
- CSSを直す時は、紙と電子書籍の両方への影響を考える（`SKILL_DIR/../../references/japanese-typesetting.md`）。紙のページを前提にした値は `@media print` に。

## 4. ビルドして検査する

本の `CLAUDE.md` の手順に従う。無ければ次のとおり。

1. `npm run build`
2. `qpdf --check <本>.pdf`、`epubcheck <本>.epub`（エラー・警告0件）
3. `python3 <道具>/check_kindle_epub.py <本>.epub`
4. 目次を手書きしている本は、目次のページ番号が本文と合っているか
5. `python3 <道具>/check_layout.py <本>.pdf --body <本文の文字の大きさ>` で泣き別れの候補を探す（本の内容がほぼ固まってからの確認版で特に。候補なので、最後はページを見て判断する）

## 5. 新旧を見比べる

```
python3 <道具>/pdf_diff_pages.py <前回の確認版.pdf> <本>.pdf --out <作業用フォルダ>/diff
```

見た目の変わったページの一覧（通し番号とノンブル）と、「旧｜新」を並べた画像ができる。

- 変わったページが、一覧の依頼の箇所と一対一に対応するか確かめる。**依頼に無いページが変わっていたら、原因を突き止めてから先へ進む。**
- 画像を実際に見て、依頼どおりに直っているか、行の溢れ・改ページのずれ・ルビの位置の崩れが無いか確かめる。
- 総ページ数が変わった時は、どこで増減したかを特定する（それ以降のページは全て「変わった」になる）。奥付・索引・目次のページ番号に響く。
- 使う人がPDFの見比べのアプリ（左右に並べて差分を示すもの）を持っていれば、新旧のPDFをそのアプリで開いて渡す。

## 6. 確認版を作る

`releases/<今日の日付>/` を新しく作る（既にある日付のフォルダは上書きしない。同じ日に2回目なら、使う人に上書きするか聞く）。中身は本の `CLAUDE.md` に従う。標準は次のとおり。

- `<書名>_確認版_<日付>.pdf`、`<書名>_確認版_<日付>.epub`
- `編集内容のご説明.md` とそのPDF（下記）
- 頼まれていれば、ルビ付きの全文Word：EPUBを展開し、`<道具>/build_word.py <展開先>/EPUB <出力.docx>`（依存: python-docx beautifulsoup4 lxml pillow。仮想環境に入れる）。pandoc はルビを落とすので使わない。

あわせて `releases/README.md` に1行（日付・主な内容・総ページ数）を足す。作業記録のファイル（`WORKLOG.md` 等）があれば追記する。

### 編集内容のご説明

著者が読む文書。IT に詳しくない人が読んで分かる言葉で書く。

```markdown
# 編集内容のご説明（<日付>版）

## 今回の主な内容
1. P.27 図3を、お送りいただいた新しい図に差し替えました。
2. P.112 後ろから3行目「さくら」を「桜」にしました。
（依頼の番号の順に。ページはノンブルで。依頼どおりにできなかった物は、理由と代わりの案）

## ページ数
240ページ（前回と同じ）。／ 242ページ（前回より2ページ増。奥付に1行足した為）

## お確かめいただきたい事
（判断を仰ぎたい事、気づいた表記の揺れ等）
```

- 変更を「著者のご指示により」と書かない。「ご依頼の反映」等、中立の言い方にする（使う人が著者でない場合、報告の宛先が変わる事がある為）。
- 前回の説明があれば引き継ぎ、冒頭に今回の節を足す。
- PDF化は `releases/<日付>/` の中で `npx vivliostyle build 編集内容のご説明.md -T "@vivliostyle/theme-base" -s A4 -l ja -o 編集内容のご説明_<日付>.pdf`（本の設定ファイルを読み込まないよう、そのフォルダで実行する。できた `themes/` は消す）。

## 7. 報告する

使う人への報告は短く：

- 依頼の一覧と、それぞれ「済み・保留（理由）・要確認」
- 変わったページ（ノンブル）と総ページ数
- 検査の結果（epubcheck・qpdf・Kindleの検査）
- 確認版の場所
- 判断を仰ぎたい事

コミット・プッシュは、本の `CLAUDE.md` で許されている時か、頼まれた時だけ行う。
